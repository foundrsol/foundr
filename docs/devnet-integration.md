# Devnet integration diagnosis

The false mismatch came from comparing the 32-character CAIP network marker
`EtWTRABZaYq6iMfeYKouRu166VU2xqa1` with the full `getGenesisHash()` response.
Official Devnet returns
`EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`. The connected Phantom public
key was already accepted; the subsequent RPC comparison produced the warning.
Changing Phantom's Testnet Mode could not fix that comparison.

`src/core/protocol.ts` now compares the full hash. `src/solana/network.ts` fixes
the endpoint to `https://api.devnet.solana.com`. Constructor overrides, mainnet
and testnet endpoints are rejected. Wallet connection, RPC validation, and
program deployment validation have independent diagnostics and UI states.
Timeouts report RPC unavailable, never a presumed wallet network mismatch.

The reviewed [Phantom connection API](https://docs.phantom.com/solana/establishing-a-connection)
returns the public key and connection status, without a documented reliable
active Solana cluster indicator. Its [Testnet Mode documentation](https://docs.phantom.com/developer-powertools/testnet-mode)
describes user settings, not a provider method for reading that selection.
SHELL therefore explicitly reports the wallet network as unverified. A list of
supported networks would not establish the selected network either.

Transactions use finalized blockhashes and fee quotes from the verified RPC.
SHELL requests `signTransaction` only, compares the returned serialized message
and verifies all signatures, persists the signed transaction, and submits only
through its own verified Devnet connection. It does not use the wallet's
`signAndSendTransaction` or silently fall back to it. This is the documented
[sign without sending API](https://docs.phantom.com/solana/sending-a-transaction).
A wallet unable to support that API is blocked. A wallet's review popup may
still reject a transaction; SHELL does not bypass the wallet's consent.

## Deployment and funding gates

The reserved program is
`H5dQjE5MxyTCcwVuDcrVH3yUTeP51t6CvBvg9T4FzPds`, using a dedicated development
key. Actual finalized RPC inspection returned **no program account**. See
[devnet-rpc-evidence.json](devnet-rpc-evidence.json) for the observed slot, hash,
time and public diagnostic values. A reserved identity is not a deployment.

The program is a manual Pinocchio program, not an Anchor program. The instruction
builders in `src/solana/instructions.ts` and `program/src/lib.rs` implement the
same four instructions. [shell-v1.abi.json](../program/shell-v1.abi.json) records
the exact wire layout. Winterwallet's own SDK/program ID/IDL cannot be substituted
for this SOL-only adaptation.

Funding and on-chain authorization require all of:

1. The exact official endpoint and full Devnet genesis.
2. A source-matched tested deployment attestation, generated by the verification
   script rather than a manually edited `verified` flag.
3. An executable program owned by the upgradeable loader with the expected
   ProgramData account.
4. Exact deployed bytecode hash/size, zero padding, deployment slot, pinned
   upstream source commit, and disclosed upgrade authority.
5. A verified current recovery package and, for deposits, a finalized available
   vault with the expected owner, PDA and data layout.

The frontend gates initialization, funding, commitment, withdrawal and retries.
The transaction adapter independently repeats RPC and deployment verification
before signing and before broadcasting. A verified RPC does not enable funding
when the program is absent or unverified.

## Recovery compatibility

The full RPC hash is deliberately separate from the immutable SHELL v1 signing
domain. The existing 32-character CAIP marker remains in the WOTS preimage and
schema-1 recovery field named `genesis`. This correction does not change an
existing intended message, key, address or encrypted package. The Rust verifier
uses the same immutable domain. A regression compares the exact old and new
client preimages; changing it silently could make a one-time key unsafe.

## Public diagnostics and verification

The expandable connection panel and `[SHELL devnet diagnostics]` console messages
contain only endpoint, expected/received RPC hash, connection public key,
provider name, program ID, deployment validation, and public failure causes.
An explicit whitelist excludes identities, passwords, keys, recovery packages,
and raw transactions. No analytics or remote logging endpoint is added.

```sh
npm test
npm run typecheck
npm run verify:upstream
NODE_USE_ENV_PROXY=1 npm run diagnose:devnet
SHELL_LIVE_RPC=1 npm run test:browser
```

There are 42 passing client/adapter/security/fee/keeper and Mainnet-isolation tests, including ten network
regressions. Ten real Chromium checks passed locally and on the public HTTPS site: provider connection without
network metadata, account changes/disconnect, mismatch and timeout behavior,
actual official RPC verification, encrypted identity creation/verification,
reload, clean-profile recovery, and responsive layout. Wallet tests inject the
documented Phantom provider interface; they do not automate a real Phantom
extension or prove its active network. The real RPC test uses a disposable public
address with zero balance and sends no transaction.

The actual compiled program now passes complete lifecycle and adversarial tests
in LiteSVM, including a full real-browser withdrawal/rotation/recovery flow.
The current Devnet RPC evidence checks both the vault and protocol program IDs;
neither exists and the dedicated deployer has zero lamports. The official faucet
returned HTTP 429. Actual Devnet create/deposit/withdraw/rotation remains blocked.
Deployment and initialization commands are in [deployment.md](deployment.md).
